# Dagger app

The authenticated web UI for Dagger, served at `app.dagger-ai.com`.

TanStack Start 1.x on React 19 and Vite 8, rendered client-side, talking to the
Go API at `api.dagger-ai.com` over REST with a Supabase-issued bearer token.

Two sibling projects are easy to confuse with this one:

- `web/` — the public marketing site, static Astro, no auth
- `api/` — the Go API this app calls

## Requirements

Node 24 (see `.nvmrc` and `engines.node` in `package.json`) and npm 11.

## Getting started

```sh
npm install
cp .env.example .env    # then fill in the three values
npm run dev
```

The dev server listens on port 3000. Set `PORT` to change it. `strictPort` is
enabled, so if the port is already taken the server fails loudly instead of
silently moving to the next one.

## Environment variables

| Variable | Purpose |
| --- | --- |
| `VITE_API_URL` | Base URL of the Go API, e.g. `https://api.dagger-ai.com` |
| `VITE_SUPABASE_URL` | Supabase project URL, used for auth |
| `VITE_SUPABASE_ANON_KEY` | Supabase anon key, used for auth |

**These are inlined at build time, not read at runtime.** Vite replaces every
`import.meta.env.VITE_*` reference with a string literal during `npm run build`,
so the values must be present when the build runs — not only when the dev server
starts. Changing them requires a rebuild.

Because they are inlined, they are also **public**: anyone can read them in the
client JavaScript. `VITE_SUPABASE_ANON_KEY` is designed for that and is protected
by row-level security. Never put a service-role key, or any other secret, in a
`VITE_*` variable.

`src/lib/config.ts` validates all three when it is imported, throwing a message
naming whatever is missing or blank. Nothing imports it yet: the auth work that
consumes these values is what will pull it into the bundle. Until then the
validation only runs in its own tests.

## Rendering model

The app is client-rendered. `src/start.ts` sets `defaultSsr: false`, so the
server returns a shell and the router renders in the browser. Only `/login` and
`/auth/callback` opt back into server rendering, with a route-level `ssr: true`.

Two consequences worth remembering when adding routes:

- Route loaders do not run on the server, so nothing fetches before first paint.
  Expect a shell, then data.
- The auth guard redirects on the client. A protected URL returns HTML and then
  redirects, rather than being refused by the server.

## Routing

File-based routing under `src/routes`. `src/routeTree.gen.ts` is generated by the
router plugin on dev and build — never edit it by hand. It is safe to delete; it
comes back.

Imports resolve through the `#/*` alias, which maps to `src/*` and is declared in
both `tsconfig.json` (`paths`) and `package.json` (`imports`).

## Styling

Tailwind 4 via `@tailwindcss/vite`, configured in `src/styles.css`. Theme tokens,
if and when they are needed, go in that file's `@theme` block.

## Deployment

The Railway service for this project uses **`/app` as its root directory**
(not the repository root).

Railpack installs with `npm ci`, runs `npm run build`, and starts the generated
Nitro server at `node .output/server/index.mjs`, which binds to the `PORT`
Railway provides. Node 24 is declared in both `.nvmrc` and `engines.node` — keep
the two in sync if you move to a new major.

Set the three `VITE_*` variables in the Railway service's build variables. They
are baked into the bundle at build time, so a runtime-only variable will not
reach the client.

## CI

`.github/workflows/ci-app.yml` runs on changes under `app/**`: `npm ci`,
`typecheck`, `biome ci`, `test`, `build` on Node 24.
